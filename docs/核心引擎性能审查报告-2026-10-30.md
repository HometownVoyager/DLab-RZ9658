### 2.2 12 万步堆采样

4 芯片+8 线场景连续 `step()` 120,000 步，定时取样 `heapUsed`：13→58 MB 锯齿振荡，每次 GC 回落后基线不抬升，无台阶式增长 → **无泄露**。引擎侧 `_netsCache`、`_aliasCache`、板载驱动表均为构造期建立或脏失效重建，不存在按步增长的容器。

### 2.3 契约风险记录（不阻断）

`onStateUpdate` 订阅：引擎持有监听器引用，退订依赖其返回函数（[engine.js:1622](<Teaching App/src/core/engine.js#L1622>)）。当前订阅者均为页面生命周期单例，无碍；未来若出现动态订阅（如实验面板插拔）须成对退订，否则引擎实例会被闭包钉住。已列入 §9 建议。

## 5. 已实施优化明细（全部行为等价验证）

### 5.1 H2 混叠告警缓存（省 2.2 µs/step）

- 问题：`_collectAliasWarnings` 每步经 `_buildState` 触发（[engine.js:1557](<Teaching App/src/core/engine.js#L1557>)），全量重扫所有时序芯片时钟引脚；结果只取决于网表/时钟配置/观测步长。
- 改动：构造器加 `_aliasCache/_aliasDirty`（[engine.js:291](<Teaching App/src/core/engine.js#L291>)）；扫描体搬入 `_scanAliasWarnings`（[engine.js:972](<Teaching App/src/core/engine.js#L972>)），`_collectAliasWarnings` 变为缓存门面（[engine.js:964](<Teaching App/src/core/engine.js#L964>)）。失效点：`_touchNets`、`setPower`、`setClockEnabled`、`setDds`/`adjustDds`（改频率/幅度）、`mountChip`/`unmountChip`、`reset()`；P7 观测步长变化同样置脏。
- 验证：命中时两次调用返回同一数组引用；`setDds({freqHz:500000})` 后置脏重扫；套件全绿。缓存数组为实例内共享，**消费方只读**约定已写入 JSDoc。

### 5.2 H3 芯片引脚映射预建

- 问题：`_pinLevels`/`_evalChips` 每步对每个引脚做 `_parseSocket`（字符串解析）+ `findJack` 查表。
- 改动：`mountChip` 时构建 `jackByPin`（脚号→插孔，[engine.js:825](<Teaching App/src/core/engine.js#L825>)）；`_pinLevels` 优先读缓存（[engine.js:1103](<Teaching App/src/core/engine.js#L1103>)）；`_evalChips` 惰性 `info` + `hasOwnProperty` 守卫，异常回落原路径（[engine.js:1138](<Teaching App/src/core/engine.js#L1138>)）。

### 5.3 H5 板载驱动源角色预推

- 问题：`_collectBoardDrivers` 每步用正则逐条重推插孔的板载驱动源角色。
- 改动：`_indexGeometry` 建索引时经 `_inferDriverRole`（[engine.js:371](<Teaching App/src/core/engine.js#L371>)）一次算好 `role`（[engine.js:326](<Teaching App/src/core/engine.js#L326>)），`_collectBoardDrivers` 直接消费（[engine.js:904](<Teaching App/src/core/engine.js#L904>)）。
- 关键保持：断电时仍写 `LZ`（分支顺序 pwr→gnd→断电 LZ→sw→clock→pulse→dds 不变），`_analyzeSink` 读 `net.drivers` 定电源类型（关断开关='dc'）的语义不变。

### 5.4 H8 UI 推进分工（每帧省 386.9 µs）

- 问题：Timeline 接管推进（`isOwner()`）期间，Interaction 的 rAF 每帧仍 `engine.step(now)`；相同时间戳幂等返回，但幂等本身要走收敛检查 + `_buildState`，实测浪费 386.9 µs/帧。
- 改动：Interaction 构造器接受 `opts.getTimeOwner`（[interaction.js:88](<Teaching App/src/ui/interaction.js#L88>)），`_tick` 有所有主则跳过 step（[interaction.js:745](<Teaching App/src/ui/interaction.js#L745>)）；`refresh(force)` 末尾显式无参 `engine.step()`（[interaction.js:886](<Teaching App/src/ui/interaction.js#L886>)），补上接线类操作（契约 §5：addWire/removeWire/clearWires 不自动 step）的重算；[app.js:482](<Teaching App/src/app.js#L482>) 装配传入。
- 收益：60fps 下约省 23.2 ms/秒 单核。契约见 [CONTRACTS.md:208](<Teaching App/docs/CONTRACTS.md#L208>)。

### 5.5 H9' 状态同步引用快路径（暂停帧省约 25–30 µs）

- 问题：`_syncState` 每帧做 JSON 签名比对（[interaction.js:562](<Teaching App/src/ui/interaction.js#L562>)、[858](<Teaching App/src/ui/interaction.js#L858>)）；暂停/无变化帧也要付 25.2 µs，连同短路/告警相关路径约 ×3。
- 改动：手写递归签名被测量否决（§6.2），改为引用快路径——引擎 `_buildState` 每次返回全新对象，引用相同 ⇒ 内容必同（[interaction.js:834](<Teaching App/src/ui/interaction.js#L834>)）；签名函数保留作后备。

### 5.6 P7 步长观测接线

## 6. 测量否决项

### 6.1 H4：收敛中途跳过 netInfo 构建（+16%，回滚）

设想迭代中途不构建 netInfo、末轮补一次"仅信息"全量 pass。实测 4 芯片场景 560.6 → 650.1 µs/step（**+16%**）：组合收敛迭代次数很低（多数 1–2 轮），省下的 info 构建远小于多出的整轮 levels 扫描。三处编辑全部回滚，基线复测回到 560 左右。

### 6.2 手写 sigValue 签名（慢 46%，回滚）

设想绕开 `JSON.stringify` 手写递归签名；实测 36.7 vs 25.2 µs——原生 stringify 走 JIT C++ 快路径，JS 手写难敌。目的改由 §5.5 引用快路径达成。

### 6.3 教训

两项"显然更优"的改动均被测量否决：**热点优化必须先测后留**；小迭代次数场景下"减少中间构建"可能引入更贵的收尾全量扫描。

## 7. 分析留档项（本轮不改，需设计轮）

### 7.1 H1 `_buildState` 每步全量构建（最大潜在收益 ~40%）

每步新建完整 state 并全量遍历。若"状态未变则跳过/复用"，空板与静置场景收益最大；但 state 按契约每步为全新对象（H9' 与 onStateUpdate 消费方均依赖此点），需要"冻结复用 + 显式失效"设计，并审计全部消费方（UI + CDP 测试）。

### 7.2 H6 单帧步数上限（最坏帧 46–116 ms）

`MAX_STEPS_PER_FRAME=200`（[timeline.js:17](<Teaching App/src/ui/timeline.js#L17>)）打满时，按基线 0.23–0.58 ms/步折算最坏帧约 46–116 ms，中位场景约 75 ms——逼近上限即可能可感知掉帧。建议：帧预算推进（每帧给 step ~6–8 ms 预算，超出留给下一帧）或下调上限。

### 7.3 H7 P1 批量调用逐步放大

P1 契约让 11 个变更类 API 各自自动 `step(_now)`；UI 批量操作（导入/连续拖拽）会放大为 N 次逐步推进。可在批量入口加"收尾单步"包装（需修订 P1 契约与测试）。

### 7.4 状态签名收窄

`_stateSignature` 覆盖 288 项 `jacks` 与 `segs`，视觉路径并不消费全部字段；收窄可进一步省签名耗时，但会改变 `'dlab:state'`/onState 的触发粒度，须先审计消费方。

### 11.1 H1' 同刻记忆化（显式失效，§7.1 的落地设计）—— 已实施 ✅

- **设计取舍**：§7.1 原设想「冻结复用 + 显式失效」需要审计全部消费方且 state 按契约每步全新。落地改为更安全的**同刻记忆化**：step 结果只取决于 (now, 电气状态)，变更类 API / 接线 / reset 经 `_touchState()` 置脏，「同一时刻且未置脏」的重入 step 直接复用上次状态对象（`_stateNow` 比对）。真实求值仍每步产生全新对象——「每步全新对象」的既有消费方契约不变，只是「无变更的同刻重入」不再新建。

- **引擎**：`beginBatch()/endBatch()`（嵌套按深度计数，须 try/finally 配对）；批量期间 11 个 P1 变更 API 经 `_stepAfterChange()` 延迟，`endBatch` 深度归零且确有变更时统一收尾一次。批量期间读取为延迟一致（与接线类 API 既有约定同口径），契约已写入 CONTRACTS §5。
- **接线点**：`persistence.applyProject`（导入，含旧引擎存在性守卫）、`grader` 真值表行循环与开关恢复段。
- **收益（bench BATCH vs BATCHWRAP，同一段 16 开关 + 4 芯片 + 20 导线导入型序列）**：**~2270 → ~470~670 µs（跨多轮 -71%~-79%）**。判分表每行从 2 次全量收敛降为 1 次。
- **锁定**：engine.selftest 组 21（延迟一致、恰好一次通知、嵌套、空批量、异常 finally 配对）。

### 11.3 H6 帧预算推进（§7.2 落地）—— 已实施 ✅

- **设计**：`Timeline` 增 `STEP_BUDGET_MS=7`（构造项 `frameBudgetMs` 可覆盖，0 = 禁用）。单帧先无条件推 1 拍，之后每拍前检查真实耗时，超预算即把剩余积压留给后续帧（保留积压 = 逐步消化不跳时；封顶 `MAX_BACKLOG_MS=2000` 防长期超载无界滞后）；`MAX_STEPS_PER_FRAME=200` 保留为拍数兜底（触顶仍丢弃积压，既有行为）。
- **收益**：重载电路最坏帧从「200 拍 × 单拍耗时」(46~116ms) 收敛到预算附近，60fps 不再因打满上限而可感知掉帧；时钟 / DDS 相位、脉冲宽度语义不变（虚拟时间只分帧消化、不丢弃）。
- **锁定**：timeline.selftest 组 12（慢推进函数注入验证预算截断、积压保留与封顶、分帧消化、禁用口径维持 200 拍兜底）；既有全部用例组在禁用预算下运行（helper 默认 frameBudgetMs:0，避免慢机器抖动）。
